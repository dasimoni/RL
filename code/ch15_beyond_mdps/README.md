# Chapter 15 code: Beyond the Standard MDP

Code for [Chapter 15](../../chapters/15-beyond-mdps.md): partial observability, goal-conditioned RL, options and hierarchy, successor features and zero-shot representations, multi-objective RL, meta-RL, and generalization across environments. Pure Python 3.11 + NumPy (PyTorch for the DQN of `her_bitflip.py`, the FB networks of `fb_zero_shot.py`, the GRU of `rl2_bandits.py` and the PPO agent of `procgen_lite.py`; SciPy for the transport LPs and policy searches of `exercise_solutions.py`; Matplotlib for figures). Every script pins BLAS and PyTorch to one thread, fixes its seeds and prints its settings. Run from the repository root. `--quick` is a smoke test that writes no figures; a full run writes PNGs to `figures/`.

## Implementation notes

- With two hidden states, an alpha vector is a line over b(TL), so `prune` computes an exact upper envelope (convex-hull trick); numerically parallel lines must keep the higher one. Exact finite-horizon sets keep growing with vectors that differ only far in the future; epsilon-pruning removes a vector when it raises the envelope by less than epsilon anywhere.
- Finite-state controllers (memoryless, window, belief) are evaluated exactly by solving the linear system on (controller node, hidden state) pairs (Eq. 15.12).
- `her_bitflip.py` terminates an episode when the goal is reached and truncates it after n steps; the TD target bootstraps through truncation only. Rewards and termination flags are recomputed from (s', g) when a batch is sampled, so relabelled tuples are always consistent.
- `rl2_bandits.py` predicts G/H with the value head. Regressing the raw return (up to 20) through the shared GRU lets the value loss dominate the gradient: `python code/ch15_beyond_mdps/rl2_bandits.py --raw-value-target --updates 1500` (92 s, no figures) ends with regret 3.010 / 4.991 (independent / dependent), close to random (3.318 / 5.008), while the controlled run with the same schedule and the G/H target, `python code/ch15_beyond_mdps/rl2_bandits.py --updates 1500 --no-figures` (96 s), reaches 1.140 / 1.068. The printed diagnostic shows why: with the raw target the value loss's gradient on the GRU weights is a median 122 / 146 times the policy loss's (0.10 with G/H); norm clipping was active in only 6.1% / 2.5% of the raw-target updates, so it is not the main cause.
- The diagnostic computes the two gradient norms with `torch.autograd.grad(..., retain_graph=True)` before the usual backward pass, so it does not change training: the full run reproduces the earlier results exactly.
- `fb_zero_shot.py` minimizes the FB loss E_{s,a} E_{s'~rho}[(F(s,a,z).B(s') - P(s'|s,a)/rho(s') - gamma G(s,a).Bbar(s'))^2], with G(s,a) = E_{s''~P(.|s,a)}[Fbar(s'', pi_z(s''), z)] computed exactly from the known P (target networks Fbar, Bbar; pi_z greedy for Fbar), in expanded form, F'CF - 2F.(PB) - 2gamma F'C'G + const with C = E_rho[BB'], so the N x N density is never built. The FB Bellman loss printed during training *rises* as F grows from its small initial values, because the bootstrapped target grows with it; regret, not the loss, measures progress. At test time z_R is rescaled to the sphere of radius sqrt(d) from which the training z were drawn; scaling a reward does not change its optimal policy.
- `deep_sea_treasure.py` floors the time weight at 1e-6: at w = (1, 0) every policy that eventually reaches 124 is optimal and a greedy policy may wander indefinitely.
- `procgen_lite.py`: the PLR score is the positive value loss of robust PLR (mean of max(GAE, 0) over each level's segment in a rollout); the original PLR default is the L1 value loss. An unseen training level is tried with a fixed probability 0.5 (the original PLR replays with probability equal to the fraction of training levels already seen). Training success is measured on the first min(N, 200) training levels. Time-outs bootstrap from V(last state); reaching the goal terminates. Training levels are seed * 100000 + i, held-out levels 10,000,000 + j, so no held-out level is ever trained on.
- Single-threaded BLAS matters on a shared machine: with multithreaded BLAS a 206 x 206 linear solve took about 0.75 s instead of 0.7 ms here.
